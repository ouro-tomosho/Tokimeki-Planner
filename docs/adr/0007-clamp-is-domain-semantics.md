# 夹逼是领域语义，不是实现细节

**Status**: accepted（2026-10-06 裁决；2026-10-09 复核：精确求解已移除，纪律不变）

## 决策

**属性结算时的夹逼属于领域语义，不属于实现细节。** 任何用来判定"某组目标能不能达成"的模型，
都必须使用与真实引擎**逐位一致**的夹逼语义；做不到就必须显式证明等价，不得默认忽略。

由此推出三条硬纪律：

1. **忽略夹逼的线性模型是真实系统的下界，不是上界。**
   夹逼在 0 处**只会把值抬高**（已经归零的属性不再被负效果继续拉低）。所以"不夹逼"描述的是一个
   **更穷**的系统：它承受了真实系统不承受的损失。在这个更穷的系统里得出的"不可行"，**不能移植**
   到真实系统。
2. **"不可行"这种结论必须由与引擎同源的口径给出。**
   允许用线性/松弛模型做**上界**论证（"连放宽都不可行，那真实一定不可行"——只要那个松弛**确实**
   是放宽）。不允许用它做下界方向的否定结论（"线性版不可行，所以真实不可行"）。
   **因此**：任何由模型得出的"不可行"，都必须附一句**方向论证**——*"本模型是真实系统的 □ 超集 /
   □ 限制，理由是……"*。答不上来就不能下结论，只能写"未判定"。
   两种最容易犯的形态：**把"限制"误当"放宽"**（例如给硬下界行写 RHS 时用了阈值本身而不是
   "阈值 − 已达成部分"）；以及**把吸收量变量无条件放开**（模型凭空抬高属性 = 可行域变大，
   而补上互补约束又会变成限制，两侧都不安全）。
3. **"往 0 压再拉起"（夹逼套利）是合法策略，但不推荐。**
   把某条属性长期压在 0、让它吸收所有负效果、最后再猛拉达标——这是规则的真实后果，工具不得
   假装它不存在。但求解器应当**优先寻找不依赖它的解**。
   自 2026-10-06 起，全局约束的硬阶段使多数套利日程不再合格，因此这条现在是"合法但与合格性冲突"。

**怎么保证**：夹逼必须由**求解与判定共用同一口径**来保证——求解器按 `expectedEffects` 逐日推进
（每一步都夹在 `[min, max]` 内），判定器用真实引擎 `apply()` 逐日复核。任何"靠惩罚逼出正确行为"
的写法都不可接受：那会给出**声明值与真实重放两套数**的日程。
历史上精确求解时代用过 0-1 精确编码写进 MILP 的办法（两个方向各一个 0-1 变量，使
`v = clamp(pre, min, max)` 成为唯一可行解）；那套编码与它踩过的坑随精确求解一起移到了
[ADR-0009](0009-solver-architecture.md) 的历史一节。

## 硬约束 / 目标两分

- **全局约束**：每个结算日检查一次，用**当天结算后**的数值。某条属性**首次达标之后**，
  此后任何一次结算都不得越界，否则该日程**不合格**（GLOSSARY 的「硬约束阶段」）。
- **小目标与结局目标**：**只在各自的落点判定**，判定用**落点前一天的结算值**。
  落点之前怎么波动都不算违反。
- **`ok` 与 `valid` 是两个结论**：`ok` 是目标（小目标 + 结局目标）是否达成；`valid` 是硬约束
  （全局约束的硬阶段、压力上限、社团解锁与互斥、社团集训周）是否全部满足。两者都要如实报告，
  一份日程可以 `ok = true` 而 `valid = false`。
- 三类目标的**判定口径有意不一**：全局约束是"守住"，另两类是"到点交付"。
- 三类目标的**求解顺序不相等**：求解按严格字典序（全局约束 → 小目标 → 结局目标 → 超额小奖励），
  见 ADR-0009 的「目标优先级」。

## 社团集训周

- 集训周（`data/rules.json` 的 `calendar.clubWeeks`，游戏固定事实，共 6 周）的**全部平日**
  执行**当前社团**的社团指令——这是**周指令层面的强制**。违反即不合格。
- **回家社例外**：未加入任何社团时按正常平日处理（回家社不是 `rules.clubs` 里的一个社团，
  而是 `initialClub = null` 这一状态）。
- **解锁日之前不强制**：社团指令自 `rules.clubUnlockDate`（1995-04-09）起可用。
- **8 月集训周加成**：6 周里 8 月组（1995-08-13、1996-08-11、1997-08-10）的**平日**
  社团经验 **+2**；10 月组没有加成。**该周的休息日没有倍率加成**，社团经验仍是基础 **+4**。

## 背景与理由

### 事实：真实引擎有解，而忽略夹逼的线性模型说没有

用同一份**已被验证可行**的日程（喂给 `plan(input, { assignments })` 返回 `goals.ok === true`）
对照两种口径：

| 属性 | 不夹逼（线性） | 夹逼（真实引擎） |
| --- | --: | --: |
| 体力 | −42.00 | 58.38 |
| 人缘 | 20.84 | 128.14 |
| 容姿 | −416.42 | 108.27 |
| 运动 | 194.00 | 221.49 |
| 压力 | −123.90 | 28.95 |

同一份日程：线性模型读出三项深度为负、必然判死；真实引擎读出全部达标。
**差异不是数值精度问题，是模型描述的系统不是玩家面对的系统。**

### 为什么这个错误特别容易犯

夹逼在**数学上不显眼**——它写在结算函数的最后一行，看起来像"防御性编程"或"浮点保护"。
而它实际上是**游戏规则的一部分**：属性不会低于 0，所以任何想压低某项属性的副作用，在它已经
归零后会**失效**。这条规则**只有利、没有害**，因此它让真实系统严格地比线性模型更宽松——
而"模型比现实更严格"恰恰是判定可行性时最危险的偏差方向。

## Considered Options

- **照旧忽略夹逼，把线性模型当作近似**：否决。它不是近似——它改变了可行域。用它下结论会把
  "有解"报成"无解"，代价是所有者差点据错误结论下调目标数值。
- **把夹逼当作数值噪声，在结果里做后处理修正**：否决。夹逼是**路径相关**的（在哪个时点归零，
  决定了后续能吸收多少负效果），无法从线性解事后修正出来。
- **禁止夹逼套利，把"达标后不得回落"写成硬规则**：否决。那是在**用规则掩盖口径错误**。
  正确做法是：判定器对真实语义负责，排布器对"体面"负责，两者分层。
- **把夹逼写进术语与 ADR，并要求判定模型与引擎同源**（本决策）：采纳。求解侧后来用
  **0-1 精确编码**落地（ADR-0009）。

## Consequences

- **`GLOSSARY.md` 有「夹逼」条目**，并明确它是结算规则；「硬约束 / 目标」的两分结构同时入册。
- **判定与求解所用的模型必须包含夹逼。** 精确表达方式是把逐日夹逼写成 0-1 编码（ADR-0009）；
  早先"以周为节拍建累积变量"那条建议**并不精确**（同一周内平日与休息日的效果符号相反时，
  先夹后加与先加后夹结果不同），已作废。
- **线性/松弛模型仍然有用，但只能用于"上界方向"的否定结论**，且必须显式论证它确实是放宽。
- **求解器产出的每一块都必须过"对真实引擎逐日重放"的闸门**（< 1e-6），见 ADR-0009。
- **已知的悬而未决**：夹逼让"属性长期贴 0"在数值上免费，这与"游戏里长期放任某项属性归零通常
  伴随负面事件"这一实际玩法不符。本 ADR 只裁决**工具的算法**不得忽略夹逼；"是否要把套利解
  标注出来、以及标注到什么程度"由结果视图的决策承担。
