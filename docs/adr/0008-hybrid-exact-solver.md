# 单一产物：内联 HiGHS，用精确求解取代纯 JS 启发式

**Status**: accepted（2026-10-06，所有者裁决）

> **取代本文早先的"双产物"版本。** 初版决定是"默认版保持 237 KB 纯 JS + 可选精确版 5 MB"；
> 所有者随后裁决：**舍弃纯 JS 技术栈，产品改用 HiGHS WASM 做精确求解，舍弃原先的版本。**
> 于是 `index.html` 是**唯一**产物，且**内联 HiGHS**。

## 决策

**产品只交付一个 HTML：`index.html`，内联 HiGHS（WASM）。** 约 5 MB。

| | |
| --- | --- |
| 构建命令 | `npm run build`（唯一命令，无开关） |
| 产物 | `index.html`，内联 core + HiGHS + worker + app |
| 体积 | 原始约 5.0 MB；gzip 传输约 1.8 MB |
| 依赖 | 构建期需要 `highs`（`npm install --no-save highs`）；**运行时零依赖、零网络请求** |
| 交付形态 | 单文件，拷到任何地方、断网双击即可用 |

**被舍弃的**：束搜索那一代启发式求解器作为产品路径（束搜索本身、以及给它打分的分层排序键）。它们所在的模块已从仓库删除；**周配额层保留了下来**——它现在不负责"求解"，只作为构造式排布（`src/descent.js`）的暖启动初值。

## 背景与理由

### 为什么放弃纯 JS 启发式

求解器是这个工具唯一的价值主张，而纯 JS 这条路**试尽了仍然失败**，且失败原因在过程中被查清：

1. **九版排序键全败**，失败形态每次都一样（文科与毅力归零、艺术与人望超额）；
2. **加宽束无效**：K 从 8 到 512（190 倍时间），参与判定的达标数恒为 3/11；
3. **配额层是死代码**：`seed` 的有无产出**逐字节相同**的 assignments；
4. **根本原因**（见 [ADR-0007](0007-clamp-is-domain-semantics.md)）：那些启发式优化的是一个**忽略夹逼的线性世界**，而真实引擎靠夹逼才知道自己有解。在一个**没有解的问题**里加宽搜索，只会找到更多同样无解的状态。

真问题**是**一个整数规划，且规模明确可解。用现成的精确求解器解决它，比继续调启发式更诚实也更省事。

### 为什么内联而不是旁挂

`file://` 协议下浏览器禁止 `fetch('./highs.wasm')`（同源/CORS 限制），而本项目的交付承诺是**"拷一个文件到任何地方、断网双击就能用"**（[ADR-0006](0006-generated-artifacts.md)）。旁挂 wasm 会让这条承诺失效——文件必须与 HTML 放在一起，且不能双击打开。

内联则两者兼得：**单文件、零依赖、零网络请求**。代价是 HTML 从 237 KB 涨到 5.0 MB（gzip 1.8 MB），这是所有者明确接受的代价。

## 内联需要三处构建期改写（都在 `tools/inline-highs.mjs`）

HiGHS 的胶水层是 ESM（`.mjs`），而页面的 `<script>` 是**经典脚本**，且必须满足产物的"零外部资源引用"守卫：

1. **`import.meta.url` → 全局常量（空串）**。经典脚本里出现 `import.meta` 是**语法错误**；它唯一的用途是 `locateFile` 定位 wasm 文件，而我们走 `instantiateWasm` 自己喂字节，那条路径永远不会执行——所以空串是安全的，不是"碰巧能用"。
2. **ESM 导出 → 全局挂载**。胶水层被压缩过，导出语句不一定落在行首，替换不能锚定行首。
3. **剥掉唯一的 URL**：胶水层有一条错误信息带 CPLEX 格式文档链接，会命中零外链正则 `/https?:\/\//`，把主机名替换掉即可（语义不变）。

**判据用真正的语法校验（`node:vm` 的 `new Script`），不用正则**：正则会被 `await import("node:module")` 这类 Node 分支里的动态 import 误伤，而那个分支在浏览器/Worker 里永远不会执行。

## 运行时契约

- **`await globalThis.createHighs()`** 取得 HiGHS 实例（Promise 缓存，3.4 MB 的编译开销只付一次）。
- **Worker 与主线程都能拿到**：求解跑在 Worker 里，而内联脚本在主线程的 `<script>` 中，所以引导脚本必须把 `#inline-highs` 的文本**一并前置给 Worker 源**（`core + inline + worker` 三段）。漏掉这一步的表现是"主线程有、Worker 没有"，属静默失灵，因此有机械测试断言拼接顺序。
- **`WebAssembly.instantiate(bytes, imports)`（字节形式）返回 `{ module, instance }`**，而 Emscripten 的 `instantiateWasm` 回调要的是**裸 instance**。接错的报错是 `Cannot read properties of undefined`，因此有测试锁住。

## ⚠️ 精确求解的头号陷阱：**模型可行 ≠ 真实可行**

把逐日夹逼写成 MILP 时，若用"辅助变量 `L ≥ 0` 表示当天被 0 吸收掉的量"，那么 `L > 0` 而实际并不需要吸收时，模型会**凭空抬高**属性——而 LP 松弛里"凭空抬高"与"真实吸收"**同价**。

实测后果：35% 全约束跑 600 s，`mip_gap = 0.169`，抽出的解有 **1103 条终值与真实重放不一致**。

**因此这是硬门槛：任何由求解器产出的日程，都必须过"对真实引擎逐日重放"的闸**——用 `src/settlement.js` 的 `apply()` 重放，与模型声明值逐条比对（< 1e-6）。不过闸的解一律丢弃。这条与 ADR-0007 的"判定必须与引擎同口径"是同一条纪律的两个面。

## Consequences

- **`index.html` 从 237 KB 变成约 5.0 MB**（gzip 1.8 MB）。GitHub Pages 侧无障碍：仓库 1 GB / 单文件 100 MB 的限制远超需求。
- **`highs` 仍是开发期依赖**（`npm install --no-save highs`）——精确求解是"构建期把二进制烤进产物"，不是运行时依赖。
- **`plan-core.js` 仍是中间产物**，两个阶段（core → html）不变。
- **机械守卫**（`tests/exact-bundle.test.js`）：① 在**无 `fetch`、无 `document`、无 `XMLHttpRequest`** 的经典脚本沙箱里实例化 HiGHS 并解出 LP；② 改写后的文本不含 `import.meta`、不含 `https?://`、且能通过语法校验；③ 引导脚本把内联段前置给 Worker 源且三段顺序正确。
- **规模换能力是明确取舍**：5 MB 换"判定结论可信"。所有者认为这笔交易划算，因为此前所有"排不出来"的结论都建立在错误的模型口径上。

## 与其它 ADR 的关系

- **ADR-0006（生成物与构建管道）**继续有效：管道仍是"src/+data → plan-core.js → index.html"。本决策只改最终产物里内联了什么。
- **ADR-0007（夹逼是领域语义）**是本决策的动机：判定必须与引擎同口径，而这类判定需要真正的求解器。两者合起来构成一条纪律：**问题要用能表达真实规则的模型来解**。
- **取代 [ADR-0005](0005-checkpoints-and-scoring.md) 描述的打分方案**：束搜索那一代（连同它的分层排序键）已从仓库删除，0005 作为历史记录保留——想知道"换掉的那一代当时为什么那样排、又为什么没能解决问题"，读它。
