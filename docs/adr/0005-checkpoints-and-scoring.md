## 决策

`src/score.js` 是状态好坏的**唯一判据**：束搜索给每个状态算一个**排序键**，按键的**字典序**比较，保留排在前面的 K 个状态。排序键不是标量、不是求和（`src/score.js:235-251`）。

入口三层：

```
compareStates(a, b, level)          // src/score.js:342-344
  └─► keyOf(state, level)           // src/score.js:252-325
        └─► compareKeys(a, b)       // src/score.js:328-337
```

`level` 至少含 `date`；缺省时取时间轴起点（`src/score.js:253`）。

### 排序键：四层字典序

`keyOf` 返回 `{ impossible, worst, total, frozen }`（`src/score.js:317-324`）。`compareKeys` 依次比较这四层，**前一层打平才看下一层**（`src/score.js:328-337`）：

| 层 | 字段 | 现状含义 | 谁更优 |
| --- | --- | --- | --- |
| 1 | `impossible` | 判为"不可及"的属性**项数** | 0 项最优；都不为 0 时项数少者优（`:329-333`） |
| 2 | `worst = −min(done)` | 最短板完成度取负 | 数值小者优 ⇔ 最短板完成度高者优（`:334`） |
| 3 | `total = −Σ done` | 完成度之和取负 | 数值小者优 ⇔ 完成度之和大者优（`:335`） |
| 4 | `frozen = frozenPenalty / 1e6` | 冻结的过去检查点惩罚 | 数值小者优（`:336`） |

三点必须说清：

1. **没有 `1e9`、也没有"常数奖励"参与排序。** `impossible` 是计数（`src/score.js:260, 312`）；模块里导出的 `IMPOSSIBLE_PENALTY = 1e9`（`:21`）与 `SATISFIED_BONUS = 1`（`:23`）在当前排序键里**没有被读取**，仓库内只有 `tests/score.test.js` 断言它们的量级。
2. **"达标后给常数奖励"这个机制不再存在**：已达标属性只是完成度记满（`src/score.js:296-298, 300`），不额外加分。
3. **第 4 层除以 `1e6`**，为的是让它**只能在前三层完全打平时**起作用；原样带入会直接支配排序——实测 `frozen = 5000` 让比较结果变成 5000（`src/score.js:321-322`）。

### `done` 的精确定义

`done` 是某条属性在本层日期上的**完成度**（`src/score.js:288-301`）。方向取自该属性**最终检查点的方向** `base.op`（`progressBase`，`src/score.js:66-75`），**与 `reach` 有没有值无关**——2026-10-06 修正过这一点，理由见「已修正项」：

- **上限方向（`base.op === '<'`，当前只有压力）**（`src/score.js:294-298`）：
  - `current < 阈值` → `done = 1`（低于阈值记满）；
  - 否则 `done = max(0, 1 − (current − 阈值) / max(1, 阈值))`（高出多少按阈值线性衰减，最低 0）。
- **其余情况（`>=`）**（`src/score.js:299-301`）：
  - `done = max(0, min(1, current / max(1, 阈值)))`，即 `current / 阈值` 夹在 `[0, 1]`。

**分母是"目标值"，不是"起点到目标的跨度"**（`src/score.js:281-287`）。曾经写成 `(current − 起点) / (目标 − 起点)`：目标低于起点时（体力 100→50）它会**奖励往下走**，实测把体力压到 0；而且 `Math.max(0, …)` 会让 `stamina=100` 与 `stamina=0` 的键逐字段相同。

两条配套规则：

- 阈值取该属性**最后一个单属性检查点**的值（`progressBase`，`src/score.js:66-75`）。
- 没有单属性最终检查点的属性 `progressBase[i] === null`，**整体跳过**（`src/score.js:279`）：既不进 `worst` 也不进 `total`。当前只有社团经验属于这一类——它只被一个集合型小目标覆盖，而集合型检查点在 `finalByAttribute` 里被跳过（`src/score.js:54`）。一项都没数到时 `worst` 记 0（`:314`）。

### `impossible` 的两个来源

每命中一条属性 `impossible += 1`（`src/score.js:260, 273, 307`）。排序只比项数，**不淘汰状态**——被判不可及的状态照样留在束里参与比较（`tests/score.test.js:39-59`）。

**来源一：达成过的全局下限被跌破**（`src/score.js:268-274`）。某个单属性全局检查点曾在 `state.achieved` 里留下"达成"标记，而当前值不满足它的比较符时，该属性记一次不可及，并且**本轮同时退出完成度统计**（`continue`，`:273`）。`globalFloors` 的构造只取单属性全局检查点（`:44-50`）；"达成"标记由 `crossCheckpoint` 在跨检查点时打上（`src/checkpoints.js:180-184`）。这是"达成后保持"在打分里的落点。

**来源二：剩余产能不够**（`src/score.js:306-314`）。在 `info !== null` 且 `beforeHorizon`（`date < 时间轴终点`，`:255-257`）时：

```
need      = op === '>=' ? 目标 − 当前 : 当前 − 目标
available = op === '>=' ? 到终点为止的正向产能 up : 到终点为止的负向产能 |down|
need > 0 且 available > 0 且 need > available + 1e-9   →   impossible += 1
```

两个细节：**`available ≤ 0` 直接跳过、不判不可及**（`:311`）——该属性在当前配置下根本涨不了，缺口由达标清单如实报告（`src/checkpoints.js:226`）；容差是 `1e-9`（`:312`）。

### 可达性看的是该属性的最后一个检查点，且终点当天关闭

`reach[i]` 在 `levelInfo` 里构造（`src/score.js:160-179`）：取该属性**日期最大的单属性检查点**（`finalByAttribute`，`:37-64`），把从本层周锚点到它为止的逐周产能累加成 `{ op, value, up, down }`；**只有 `target.date > date` 且 `date < 时间轴终点` 时才有值**，否则为 `null`（`:168`）。

- **不是"未来最近的检查点"**（`src/score.js:37-41` 的注释记录了原因）：全局约束的落点曾经是每周六（自 2026-10-06 起是每个结算日），若看最近检查点，人缘起点 32、单周产能约 10，任何状态在起点就会被判"来不及"——判据恒真、整层报废。
- 地平线必须用**时间轴终点 `end`（1998-03-01）**，不能只用 `lastSettlement`（1998-02-28）：用后者会让终点之后的每个日期 `reach` 全为 `null`，判据整个失效（`src/score.js:160-167` 注释，实测"1998-02-28 上科研差 130 点仍被算作可达"）。
- **终点当天判据关闭**：`date < end` 这条同时出现在 `reach` 的构造（`src/score.js:168`）与 `keyOf` 的 `beforeHorizon`（`:255-257`）里，最后一层上可达性不再判定。

### 产能怎么估

`weekCapacity`（`src/score.js:77-105`）：候选池取**当周社团**下可用的指令（`:79`），对每条指令取平日 / 休息日两种**期望效果**里的最大值（`:90-100`），再乘天数：

```
up   = max(0, 平日效果) × 平日天数 + max(0, 休息日效果) × 休息日天数
down = min(0, 平日效果) × 平日天数 + min(0, 休息日效果) × 休息日天数
```

天数只数 `[起点, 最后结算日]` 内、且**跳过起点当天**的日子（`src/score.js:82-88`）。结果按 `属性|周锚点` 缓存（`:107-116`）；与日期有关、与状态无关的量（目标值、紧迫度权重、到终点的产能）按日期缓存（`levelCache`，`:118-185`）。

## 背景与理由

### 为什么必须是字典序

每周只有一条**周指令**、作用于 6 个平日，所以**一个决策同时推动全部 10 个属性**。任何把多目标折叠成单一标量的做法（求和 / 取最差 / 加权 / "可达项数"）都会丢掉"哪几项已经够了、哪一项还欠着"的信息（`src/score.js:236-240`）。实测出现过的退化解（`src/score.js:204-205, 221-223, 238-240`）：

- 文科 286 严重超额，而容姿只有 3.8；
- 体力 950 而其余归零；
- "达标项数"版本在 3 到 8 之间反复横跳。

max-min 直接表达"先补最要紧的那一项"（`src/score.js:242-244`）：最短板决定排序，已达标项完成度为 1、不再驱动搜索。

### 检查点的三种来源（现状）

| 来源 | 落点 | 判定基准 |
| --- | --- | --- |
| 全局约束 | **每个结算日**一个落点（`src/checkpoints.js:74-87`） | **落点当天的瞬时值**（`src/checkpoints.js:182-195`） |
| 小目标 | 各自的截止日 | 属性集合的**求和**（`src/checkpoints.js:19-22`） |
| 结局目标 | 最后一个检查点（终点 1998-03-01） | 各属性阈值 |

每条属性的**起点值**隐式构成它的第一个检查点（`src/checkpoints.js:116-121`）。全局约束**不进**冻结惩罚（`src/checkpoints.js:188-192`），它只由"达成后保持"（不可及来源一）与达标清单承担。

### 全局约束：每日检查 + 先达成者先硬化（2026-10-06 已落地）

所有者 2026-10-06 裁决：全局约束改为**每日检查**，语义是「先达成者先硬化」——某条全局下限**首次达成之前是软约束**（可欠着，如实计入缺口报告），**一旦达成即转硬约束**（此后任何一次结算跌破即硬违反，该日程不合格）。这套"硬约束 / 目标"两分的定义见 GLOSSARY（「硬约束 / 目标」「软约束阶段 / 硬约束阶段」「检查点的三种来源」）与 [ADR-0007](0007-clamp-is-domain-semantics.md)（它把该两分与夹逼一并入册），**本条不重复定义**。

该裁决**已于 2026-10-06 落地**：落点生成见 `src/checkpoints.js:74-87`；`crossCheckpoint` 按落点当天瞬时值记录 `achieved`（`src/checkpoints.js:182-197`）；打分侧第 1 层用它判"达成后跌破"（`src/score.js:268-274`）；达标清单侧按同一口径报 `hardViolations` 与 `state: 'violated'`（`src/checkpoints.js:210-352`）。"每周取逐日最小值"与状态里的 `weekMin` 字段一并删除。

### 排序键只读 `reach`：轨迹与紧迫度权重已成遗留计算

`levelInfo` 至今仍计算每条属性的**目标轨迹值**与**紧迫度权重**（`src/score.js:127-158`；轨迹的构造见 `src/checkpoints.js:96-135`），但 `keyOf` 只从它里面取 `reach`（`src/score.js:254`）。仓库内除 `score.js` 自身外没有消费者：`marginOf` / `levelInfo` / `trajectory` 三个导出没有任何调用点，`trends` / `weights` 两个字段建了不用。也就是说，本文件早期版本描述的"分段线性目标轨迹 + 紧迫度权重"**不再参与状态排序**，只是在每层被算出来。

轨迹本身保留了三处修正（`src/checkpoints.js:116-128`）：只有 `>=` 属性的终点检查点构成轨迹点位；全局检查点与集合型检查点不构成点位；`>=` 属性的趋势线取"起点值与插值的较高者"（`src/score.js:137-141`）。理由是上限方向（压力）的插值会产生一条**向上**的斜线，把求解器奖励成"把压力升到阈值"——实测压力被推到 999。

### 同一文件里还有三处过期注释

`src/score.js` 开头（`:1-13`）仍在描述"三段相加"的旧打分；`:199-216` 与 `:217-234` 两段注释各描述一版已被替换的排序键（"缺口分配"版、"可达目标数"版）。**只有 `:235-251` 那一段与实现一致。** 读这个文件时以 `keyOf` 的代码为准。

## 已知偏差与已修正项（代码里有、此前文档没有）

1. **产能估计只把周日当休息日，不读 `rules.calendar.restDays`**（`src/score.js:82-88`）。`weekCapacity` 用 `i === 0` 判休息日、`i = 1..6` 判平日，而周锚点就是周日（`src/dates.js:32-34`）。于是由 `rules.calendar.restDays` 标记的休息日——当前数据里 **38 天**——只要落在周一至周六，就一律按平日计入产能。真实引擎的休息日定义是 `weekday === 0 || restDays.has(date)`（`src/calendar.js:70`），且休息日效果为平日的 **4 倍**（`daily` / `club` / `stressReduction` 三个倍率当前均为 4；`src/settlement.js:30-53`），所以这份产能账只会**偏低**、不会偏高。同一仓库另一处（`src/quota.js:45-49`）明确写了"休息日不能按 `i === 0` 硬编码、要读 `restDays`"，`src/score.js` 这一处没有跟上。

2. **已修正（2026-10-06）：`held` 与检查点判定口径不一致。** 原先 `held`（`src/score.js:269-273`）读的是当层**瞬时值**，而全局检查点的"达成"记录用 `state.weekMin`（周最小值）判定（旧 `src/checkpoints.js:168`）——某周里曾跌破、但当层瞬时值已回到阈值之上的状态不会被判不可及，两处对"这一周算不算达标"可能给出不同答案。改成每日检查后，`crossCheckpoint` 与 `held` 都按**落点当天的瞬时值**（`src/checkpoints.js:183`、`src/score.js:270-272`），`weekMin` 从状态与判定里删除，这条偏差消失。

3. **已修正（2026-10-06）：终点当天 `<` 属性落进 `>=` 公式。** 原实现用 `info.op` 判方向，而 `reach` 在时间轴终点当天恒为 `null`（`src/score.js:168`），于是最后一层把压力按 `clamp(压力 / 阈值, 0, 1)` 算——**压力越高（越接近阈值）完成度越高**，实测 `keyOf(state, { date: '1998-03-01' })` 下 `stress=49` 反而排在 `stress=10` 前面（`total` 分别 −4.127435897435897 与 −3.3474358974358975）。现在方向取自 `base.op`（`src/score.js:294`），终点当天仍是"低于阈值记满"；`tests/score.test.js` 有一条用例钉住它（终点层 `stress=10` 与 `49` 的键逐字段相同，`80` 必须更差）。

## Considered Options

- **继续用正负属性总和排序（`0002` 的那一套）**：否决，**理由仍然成立**。它把 10 个属性压成一个标量，掩盖"有属性严重欠账而另一属性严重超额"这种解（`src/score.js:221-223`），并引入无法审计的权重。
- **把多目标折叠成任何单一标量（求和 / 取最差 / 加权 / 可达项数）**：否决，**理由仍然成立**（`src/score.js:236-240`）。一个决策同时推动 10 个属性，折叠会丢掉"哪几项已经够了"的信息；实测达标项数在 3 到 8 之间反复横跳。
- **保留逐日的全局约束（当时以硬约束形式否决）**：**已被所有者推翻。** 当时的理由是"逐日检查把打分频率推到 1061 次，且硬淘汰会让起步未达标的合法状态无解"。2026-10-06 所有者裁决改为每日检查、先达成者先硬化（见上「全局约束：前瞻」与 [ADR-0007](0007-clamp-is-domain-semantics.md)），本条的否决不再成立。
- **硬淘汰 `impossible` 的状态**：**结论仍成立，旧理由已失效。** 结论方面代码确实不淘汰：`impossible` 只是第 1 层，被判不可及的状态照样进束、照样可比较（`src/score.js:317-337`，`tests/score.test.js:39-59`）。但旧理由说"`impossible` 涵盖全局约束尚未达成"——当前的 `impossible`（`src/score.js:268-274, 306-314`）**只含两类**：达成过的全局下限被跌破、剩余产能不够；"全局约束尚未达成"不再计入。
- **阶梯式目标（不问中间进度）**：**随机制一同失效。** 它否决的是"分段线性目标轨迹"这一已退出排序的机制（见上「轨迹与紧迫度权重已成遗留计算」）；当前排序键既不含轨迹、也不按中间检查点分档，这条只作历史记录。

## Consequences

- **`0002` 被本决策取代，予以删除。** 本项目不再有"分层等权总和"这个目标定义；检查点表仍是目标的**唯一**表达方式（`src/checkpoints.js`）。
- **排序键读的状态字段**：`state.attributes`（`src/score.js:258`）、`state.achieved`（`:269`）、`state.frozenPenalty`（`:323`）。`weekMin` 已随每日检查取消（2026-10-06），状态里不再有它。存档与结果导出要跟得上这些字段。
- **打分之外的硬约束另报**：`plan()` 的达标清单同时给两个顶层结论——`goals.ok`（参与判定的目标是否全部达标）与 `goals.valid`（硬约束是否全部满足：全局约束的硬阶段 + 社团集训周），并逐项报 `state` / `hardViolations` / `firstAchievedDate`。本 ADR 只管打分函数；`valid` 的完整口径见 `src/checkpoints.js` 与 [ADR-0007](0007-clamp-is-domain-semantics.md)。
- **冻结惩罚只作末位决胜**：它除以 `1e6` 后排在最后一层（`src/score.js:321-323`），实测 `frozen = 5000` 只贡献 0.005，正常情况下不可能盖过前面三层。
- **分数必须缓存**：`levelCache`（`src/score.js:118-185`）与 `capacityCache`（`:107-116`）把与日期有关、与状态无关的量缓存起来；`tests/score.test.js` 断言单次 `keyOf` 低于 0.05 ms（初版实测 0.786 ms/次）。这是束搜索能在预算内跑完的前提。
