# 夹逼是领域语义，不是实现细节

**Status**: accepted（2026-10-06，所有者裁决）

## 决策

**属性结算时的夹逼（`[0, 999]`）属于领域语义，不属于实现细节。** 任何用来判定"某组目标能不能达成"的模型，都必须使用与真实引擎**逐位一致**的夹逼语义；做不到就必须显式证明等价，不得默认忽略。

由此推出三条硬纪律：

1. **忽略夹逼的线性模型是真实系统的下界，不是上界。**
   夹逼在 0 处**只会把值抬高**（已经归零的属性不再被负效果继续拉低）。所以"不夹逼"描述的是一个**更穷**的系统：它承受了真实系统不承受的损失。在这个更穷的系统里得出的"不可行"，**不能移植**到真实系统。

2. **"不可行"这种结论必须由与引擎同源的口径给出。**
   允许用线性/松弛模型做**上界**论证（"连放宽都不可行，那真实一定不可行"——只要那个松弛**确实**是放宽）。不允许用它做下界方向的否定结论（"线性版不可行，所以真实不可行"）——这正是本项目此前两次判断出错的同一个原因。

   这条纪律还有一个**更容易犯的变体**，2026-10-06 当天又踩了一次：**把"限制"误当"放宽"**。
   具体两种形态：
   - **编码写错**：给硬下界行写 RHS 时用了阈值本身而不是"阈值 − 已达成部分"，等于要求"每一天都必须达标"，模型比真实更紧；
   - **松弛用得比真实更紧**：用辅助变量 `L ≥ 0` 表示"当天被 0 吸收掉的量"时，若不加论证就断言"该模型是真实系统的超集"，忽略了一件事——**`L` 无条件放开会让模型凭空抬高属性**（模型可行域变大），而**补上互补约束（`L > 0` 仅在真正触底时允许）又会把它变成限制**（模型比真实更紧）。两侧都不是无条件安全的。

   **因此**：任何由模型得出的"不可行"，都必须附一句**方向论证**——*"本模型是真实系统的 □ 超集 / □ 限制，理由是……"*。答不上来就不能下结论，只能写"未判定"。同理，"把负效果全部白送"那种松弛之所以可信，正是因为它能明确论证为**超集**。

3. **"往 0 压再拉起"（夹逼套利）是合法策略，但不推荐。**
   把某条属性长期压在 0，让它吸收所有负效果，最后再猛拉达标——这是规则的**真实后果**，工具不得假装它不存在。但求解器应当**优先寻找不依赖它的解**，并在结果里**标注**哪些属性段依赖了套利。
   **自 2026-10-06 起，全局约束的硬阶段使多数套利日程不再合格**（见下条），因此这条现在是"合法但与合格性冲突"。

## 同日追加的三条裁决（2026-10-06，所有者）

所有者在本 ADR 落地过程中追加裁决了三件事，前三件与上文的硬约束/目标两分直接相关：

### 一、全局约束：达标后**不得再越界**；小目标与结局目标只管落点

- **全局约束**：某条属性**首次达标之后**，此后任何一次结算都不得越界（返回未达标侧），否则该日程**不合格**。这与 GLOSSARY 的「硬约束阶段」是同一条规则，此处明确它在**每一次结算后**检查，而不是每周一次、也不是只看落点。判定用**当天结算后**的数值。
- **小目标与结局目标**：**只在各自的落点判定**，判定用**落点前一天的结算值**。落点之前怎么波动都不算违反（只要落点达标）。
  这条澄清了此前"三类目标判定口径不一"的含糊之处——不一是**有意的**：全局约束是"守住"，另两类是"到点交付"。
  取值口径同样是有意不一的：全局约束看**当天结算后**，另两类看**落点前一天的结算后**（即落点当天的结算不计入）。结局目标的落点是时间轴终点、当天不结算，所以两者在它身上恰好重合。

### 二、`goals.ok` 与 `goals.valid` 是两个不同的结论

- `goals.ok`：**目标**是否达成（小目标 + 结局目标），语义不变；
- `goals.valid`：**硬约束**是否全部满足（全局约束的硬阶段、压力上限、社团解锁与互斥、社团集训周）。

**两者都要如实报告。** 一份日程可以 `ok = true` 而 `valid = false`——这正是仓库根那份两阶段日程的处境：11 项目标全部达标，却让体力跌破 503 天、容姿跌破 910 天（两者都到过 0）。

### 三、社团集训周：整周平日都执行社团指令；回家社例外

`data/rules.json` 的 `calendar.clubWeeks` 是**游戏固定事实**（该文件的 `calendar.note` 写明"由所有者逐日核对过，解析器只读"），语义为：

- 集训周的**全部平日**执行**当前社团**的社团指令——是周指令层面的强制，不是单日强制；
- 使用者若选择**回家社（即不加入任何社团）**，集训周**按正常平日处理**，不做强制。

**「回家社」在数据里不是一个社团**：`rules.clubs` 的 11 个社团里没有它，它对应的是 `initialClub = null`（未加入社团）这一状态——此时 `clubAt()` 返回 `null`，没有任何社团指令可选，集训周自然无从强制。

**此前这条规则没有任何代码执行**：全仓只有 `src/quota.js:135-136` 读它，`buildCalendar` 不读、`input.js` 不校验、`plan.js` 不报错；实测把集训周改成 `cmd-study-science` 后 `plan()` 仍返回 `ok: true`、`problems: []`。**这是必须补上的硬约束。**

### 四、8 月集训周的社团经验加成：只作用于平日

`rules.calendar.clubWeeks` 的 6 条恰好分为两组，结构对称：

| 组 | 日期 | 加成 |
| --- | --- | --- |
| **8 月组** | 1995-08-13、1996-08-11、1997-08-10 | **集训周平日社团经验 +2**（基础 +1 的 2 倍） |
| 10 月组 | 1995-10-08、1996-10-06、1997-10-05 | **无加成**（平日仍 +1） |

两条边界由所有者明确：

- **「集训周」只包含那一周的平日**，不包含休息日。因此**该周的休息日没有倍率加成**，社团经验仍是基础值 **+4**。
  （即：不存在"休息日在集训周里所以也 ×2"这回事；"×2"的作用域就是"集训周的平日"。）
- **10 月的三个集训周没有加成**，只有 8 月组有。

净效果：8 月集训周的平日 `+2` 与「该周平日被强制为社团指令」叠加，使这 3 周成为**免费收割社团经验的窗口**（3 周 × 约 6 个平日 × +2 ≈ 36 点）。这是把「社团经验 ≥ 380」这个默认小目标变得可达的重要一条。


## 背景与理由

### 事实：真实引擎有解，而线性模型说没有

`src/settlement.js` 每次结算后把每条属性夹在 `[min, max]`。而本项目历史上全部"默认目标不可行"的结论，都建立在**忽略夹逼**的模型上：开发期先后用过多种规模的松弛 LP 与 MILP（周粒度与逐日都有），它们无一例外地跳过了夹逼。

用同一份**已被验证可行**的日程（喂给 `plan(input, { assignments })` 返回 `goals.ok === true`，11 条参与判定的目标全达标）对照两种口径：

| 属性 | 不夹逼（线性） | 夹逼（真实引擎） |
| --- | --: | --: |
| 体力 | −42.00 | 58.38 |
| 人缘 | 20.84 | 128.14 |
| 容姿 | −416.42 | 108.27 |
| 运动 | 194.00 | 221.49 |
| 压力 | −123.90 | 28.95 |

同一份日程：线性模型读出三项深度为负、必然判死；真实引擎读出全部达标。**差异不是数值精度问题，是模型描述的系统不是玩家面对的系统。**

### 为什么这个错误特别容易犯

夹逼在**数学上不显眼**——它写在结算函数的最后一行，看起来像"防御性编程"或"浮点保护"。而它实际上是**游戏规则的一部分**：属性不会低于 0，所以任何想压低某项属性的副作用，在它已经归零后会**失效**。这条规则**只有利、没有害**，因此它让真实系统严格地比线性模型更宽松——而"模型比现实更严格"恰恰是判定可行性时最危险的偏差方向。

### 同类错误在本项目已发生过一次

开发期的规格里已经记录过一条同类教训：*"线性值为负、被 [0,999] 截断到 0 是合法的"*。当时的结论是"**线性终值 ≥ 0 ⇒ 不可达**"这条判据作废。但那条教训没有被推广到"用线性模型整体判定可行性"上，于是同一个坑在下一轮又踩了一次。

## Considered Options

- **照旧忽略夹逼，把线性模型当作近似**：否决。它不是近似——它改变了可行域。用它下结论会把"有解"报成"无解"，代价是所有者差点据错误结论下调目标数值。
- **把夹逼当作数值噪声，在结果里做后处理修正**：否决。夹逼是**路径相关**的（在哪个时点归零，决定了后续能吸收多少负效果），无法从线性解事后修正出来。
- **禁止夹逼套利，把"达标后不得回落"写成硬规则**：否决。那是在**用规则掩盖口径错误**——把一个真实存在的自由度藏起来，日后必然以别的形式再爆一次。正确做法是：判定器对真实语义负责，排布器对"体面"负责，两者分层。
- **把夹逼写进术语与 ADR，并要求判定模型与引擎同源**（本决策）：采纳。

## Consequences

- **`GLOSSARY.md` 新增「夹逼」条目**，并明确它是结算规则；「硬约束 / 目标」的两分结构同时入册。
- **判定与求解所用的模型必须包含夹逼。** 高保真表达方式：以周为节拍对每条属性建累积变量并给 `[0, 999]` 的界，夹逼即由等式 + 界精确表达（该等式是线性的）。
- **线性/松弛模型仍然有用，但只能用于"上界方向"的否定结论**：如果连一个真正的放宽模型都不可行，真实系统一定不可行。使用时必须**显式论证它确实是放宽**。
- ~~开发期的精确求解器（HiGHS）继续只作工具使用，不进产物~~ **本句 2026-10-08 作废**：
  所有者当天裁决产品改用 HiGHS 精确求解（[ADR-0009](0009-exact-solver-wired-up.md)）。HiGHS 仍在**一个文件**里
  （内联进 `index.html`），零外链、零网络请求，所以与 [ADR-0006](0006-generated-artifacts.md) 的单文件铁律并不冲突。
  同时 0009 给出了本 ADR 要求的**精确 0-1 夹逼编码**——本 ADR 当时只写到「以周为节拍建累积变量」这一层，
  而那条建议并不精确：同一周内平日与休息日的效果符号相反时，先夹后加与先加后夹结果不同。
  另：本 ADR 正文（如第 55 行）引用的 `src/quota.js` 已于同日随启发式求解器一并删除，
  正文里的引用只作历史记录。
- **已知的悬而未决**：夹逼让"属性长期贴 0"在数值上免费，这与"游戏里长期放任某项属性归零通常伴随负面事件"这一实际玩法不符。本 ADR 只裁决**工具的算法**不得忽略夹逼；"是否要把套利解标注出来、以及标注到什么程度"由结果视图的决策承担。
