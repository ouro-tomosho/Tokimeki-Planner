# 规划起点恒为已玩到，历史概念作废

**Status**: accepted

## 决策

时间轴起点恒等于**已玩到**：规划区间是 [已玩到, 1998-03-01]。已玩到那一天是**状态快照**——它的结算已经发生在游戏里，因此不再结算，规划实际从次日开始。术语上保留「已玩到」（`playedUpTo`），删掉「起点」这个说法。

因此时间轴以内不存在"起点之后、已玩到之前"的那一段，`重算起点` 与 `冻结前缀` 两个概念、求解器里的冻结前缀逻辑、日历的「历史」格状态一并删除。

## 背景与理由

本工具的用法是周期性的：玩完一段回来，改「已玩到」和属性，再看下一段怎么排。旧模型允许起点早于已玩到，于是需要一整套"冻结前缀 / 重算起点"的机器来保证"历史不被改写"。所有者裁决把这台机器连同它服务的概念一起取消：既然每次都是从"现在"重排，历史就没有落点。

## Considered Options

- **保留两个日期，只合并界面控件**：左栏少一个输入框，但内部仍允许 起点 < 已玩到，"重算起点 / 冻结前缀"继续存在——"合并"名不副实。
- **起点当天照常结算**：会把已玩到那天算两遍——旧计划为求状态结算过它一次，新计划再结算一次，属性会持续漂移。
- **起点当天为状态快照、不结算（本决策）**：与"已玩到"的过去式含义一致，且把原本写死的"起点为 1995-04-04 时当日不结算"收敛成一条通则。

## Consequences

- **失去"从更早处规划、保留已玩段"的能力**。若将来要恢复，那是一个新需求（需要一个明确的"已玩段不可改写"契约），不是把旧机器搬回来。
- 日历格状态由六态变五态（平日 / 周日 / 休息日 / 空过 / 时间轴外）；「已玩到」不再是日历内部的一条竖线，而是时间轴的左端。
- 「时间轴第一天永不结算」取代 `startDate === timelineStart` 这条特例；默认起点 1995-04-04 的既有行为不变。
- 求解器不再需要 `previous` 与 `fromDate`，冻结前缀逻辑删除。
- 旧版本导出的 JSON（可能 起点 < 已玩到）导入时：已玩到取两者的较晚者，不提示。
